# 5. PRINCIPIOS MAESTROS DEL PRODUCTO

Debes seguir permanentemente estos principios.

## 5.1 Simple para el usuario

La complejidad interna no debe trasladarse al usuario.

Cliente:

```text
¿Qué tengo que hacer hoy?
```

La respuesta debe ser evidente.

Coach:

```text
¿Qué clientes necesitan mi atención?
```

También debe ser evidente.

---

## 5.2 Personalización real

Si algo está definido como personalizado, debe existir una estructura de datos que lo permita.

No utilizar "personalizado" como simple lenguaje comercial.

---

## 5.3 Datos antes que intuición cuando existan datos suficientes

El sistema debe permitir al coach tomar decisiones basadas en:

- cumplimiento;
- rendimiento;
- peso;
- medidas;
- fotografías;
- entrenamientos;
- asistencia;
- reservas;
- hábitos;
- observaciones;
- evolución.

Los datos deben ayudar a decidir.

No deben existir únicamente para llenar tablas.

---

## 5.4 El sistema debe reducir trabajo manual

Cada funcionalidad debe evaluarse preguntando:

> ¿Esto realmente ahorra tiempo al coach?

Si una funcionalidad agrega más trabajo que valor, debe cuestionarse.

---

## 5.5 El producto debe poder crecer

No diseñar únicamente para:

```text
1 coach + 5 clientes
```

Pero tampoco construir una infraestructura empresarial innecesaria para:

```text
1 coach + 20 clientes
```

La arquitectura debe ser:

**simple ahora + preparada para crecer después.**

# 16. SEGURIDAD Y RLS

La seguridad no es una funcionalidad opcional.

Un cliente nunca debe poder:

- consultar otro cliente;
- modificar información de otro cliente;
- acceder a planes ajenos;
- acceder a fotografías ajenas;
- manipular información del coach;
- modificar datos administrativos.

Supabase RLS debe utilizarse correctamente.

La seguridad debe existir:

```text
FRONTEND
+
BACKEND
+
DATABASE
```

Nunca confiar únicamente en ocultar botones.
